## 1. Purpose

InsureAssist is a knowledge assistant. Authorized users upload insurance-related PDF documents and ask questions in natural language. Each answer is grounded in retrieved passages and carries citations to a document and page.

InsureAssist is **not** a decision-making system. It does not decide claims, underwriting, coverage or pricing. Its answers may be wrong, and the product must say so (see FR-GEN-07).

## 2. Scope

### 2.1 In scope (v1)

- Uploading and ingesting text-based PDFs, keeping track of which page each passage came from.
- Hybrid retrieval: semantic search (Sentence Transformers + FAISS) combined with keyword search (BM25), with optional cross-encoder reranking.
- Grounded answer generation with Gemini, structured citations and explicit abstention.
- JWT authentication, role-based access control (RBAC) and document-level authorization.
- An evaluation framework for retrieval and generation quality.
- Structured logging, audit events, health checks.
- Local deployment with Docker Compose.
- Cloud deployment *planning* (M7). Provider-specific infrastructure is built only after approval.

### 2.2 Non-goals (v1)

| Non-goal | Rationale |
|---|---|
| OCR for scanned PDFs | Deferred. Scanned PDFs are detected and produce a warning (FR-ING-06). |
| Automated insurance decisions or advice | Out of product scope; regulatory and liability risk. |
| Multi-tenancy (multiple organizations) | Single organization assumed (A-01). |
| SSO / OIDC / external identity provider | Local accounts with JWT first; an IdP integration is a candidate for M7. |
| Self-service user registration | Users are created by an administrator through a CLI (A-05). |
| Non-PDF formats (DOCX, HTML, email) | Future enhancement. |
| Table and figure understanding | Plain text extraction only. Table structure may be lost (documented limitation). |
| Multi-turn conversational memory | Each query is answered independently in v1. |
| Streaming responses | Possible future UI improvement. |
| Horizontal scaling of the API | v1 runs a single API worker holding the in-process indexes ([ADR-0009](decisions/0009-single-process-indexes-and-background-ingestion.md)). |
| LangChain, LlamaIndex, Redis, Celery, Kubernetes | Excluded by the frozen stack; adding any of them requires approval. |

## 3. Assumptions

| ID | Assumption | Impact if wrong |
|---|---|---|
| A-01 | One organization (single tenant). | Tenancy would need to be added to every table and every filter. |
| A-02 | Corpus up to ~200 documents / ~50,000 chunks in v1. | Exact FAISS search and in-memory BM25 would need to be revisited (IVF/HNSW, an external search engine). |
| A-03 | Documents are mostly English. | `all-MiniLM-L6-v2` is English-centric; a multilingual model would be needed. |
| A-04 | CPU-only execution for embeddings and reranking. | Latency targets assume CPU; a GPU would only make things faster. |
| A-05 | Users are provisioned by an admin through a CLI command; no registration endpoint. | A user-management API would be needed. |
| A-06 | Sample documents are synthetic, generated by project scripts, with fictional organization names. | Licensing and confidentiality review needed for any external document. |
| A-07 | A Gemini API key is available for M3+ live runs. All automated tests use a mocked provider. | Without a key, live generation and LLM-judge evaluation cannot run; everything else still works. |
| A-08 | The local machine runs Windows 11 with Docker Desktop; containers run Linux. | Paths and scripts are written to be cross-platform. |
| A-09 | Access grants are set at upload time. Changing them later is an admin CLI operation in v1 (no grants endpoint in the frozen API list). | A grants endpoint would be added with approval. |

## 4. Actors and roles

| Role | Capabilities |
|---|---|
| `viewer` | Sign in; list, view and query documents they are authorized for; submit feedback. |
| `editor` | Everything `viewer` can do, plus upload documents, share them with roles or users at upload, and delete documents they own. |
| `admin` | Everything, on all documents: delete any document, view evaluation runs, request retrieval diagnostics. |

**Document read rule (authoritative, used everywhere):** user *U* may read document *D* if and only if
`D.status = 'ready'` **and** (`U` has role `admin` **or** `D.owner_id = U.id` **or** a `document_access` grant exists for (`D`, `U`) **or** a grant exists for (`D`, any role of `U`)) **and** `U.is_active`.

## 5. Functional requirements

Each requirement has an acceptance criterion (AC) that a test can check, and the milestone (MS) that delivers it.

### 5.1 Ingestion (FR-ING)

| ID | Requirement | Acceptance criterion | MS |
|---|---|---|---|
| FR-ING-01 | Validate uploads: `.pdf` extension, `%PDF-` magic bytes, size ≤ `MAX_UPLOAD_MB`, page count ≤ `MAX_PDF_PAGES`, not encrypted, parseable. | Oversized, wrong-type, encrypted, truncated and zero-page files are rejected with a specific error code and no partial records are left behind. | M1 |
| FR-ING-02 | Extract text page by page with PyMuPDF. | For a fixture PDF with known text on each page, the extracted text for page *n* contains page *n*'s known sentence and no other page's. | M1 |
| FR-ING-03 | Normalize text (Unicode NFKC, whitespace, de-hyphenation across line breaks). | Unit tests cover each normalization rule. | M1 |
| FR-ING-04 | Split into chunks with configurable size and overlap; chunks never cross page boundaries. | Every chunk has `page_number`; no chunk exceeds `CHUNK_SIZE_CHARS`; consecutive chunks on a page overlap by about `CHUNK_OVERLAP_CHARS`. | M1 |
| FR-ING-05 | Compute a SHA-256 checksum and deterministic document/chunk IDs; detect duplicates. | Ingesting the same bytes twice gives the same `document_id` and chunk IDs; the second upload is reported as `duplicate_document`. | M1 |
| FR-ING-06 | Detect likely scanned PDFs and warn. | A fixture made only of images produces the warning `likely_scanned` and status `failed` with `no_extractable_text`; a mixed PDF produces a per-page warning. | M1 |
| FR-ING-07 | Produce a structured ingestion report (JSON). | The report validates against the `IngestionReport` schema and includes counts, warnings, errors and timings. | M1 |
| FR-ING-08 | Export document and chunk records as JSONL. | Exported files round-trip through the Pydantic models without loss. | M1 |
| FR-ING-09 | Upload through the API is asynchronous, with status `processing → ready / failed`. | `POST /documents` returns 202; polling `GET /documents/{id}` eventually shows `ready` or `failed`. | M5 |

### 5.2 Retrieval (FR-RET)

| ID | Requirement | Acceptance criterion | MS |
|---|---|---|---|
| FR-RET-01 | Embed chunks and questions with a configurable Sentence Transformers model (default `all-MiniLM-L6-v2`), L2-normalized. | Embedding dimension matches the model; vector norms equal 1 ± 1e-5. | M2 |
| FR-RET-02 | Persist the FAISS index and a manifest; load it at startup; rebuild it from canonical chunk data. | A rebuild from canonical data gives the same vector-ID set and search results as the incremental index. | M2 |
| FR-RET-03 | Keep a stable mapping between vector IDs and chunk IDs. | `vector_id` is derived deterministically from `chunk_id`; collisions are detected and fail the build. | M2 |
| FR-RET-04 | BM25 keyword index over chunk text. | A query containing an exact rare term (e.g. a policy form number) returns the chunk containing it in the top 3. | M2 |
| FR-RET-05 | Hybrid retrieval merged with Reciprocal Rank Fusion; configurable `candidate_k` and `top_k`. | Results include per-retriever ranks/scores and the fused score; ordering is deterministic for equal inputs. | M2 |
| FR-RET-06 | Restrict retrieval to authorized documents; re-check the ACL before generation. | No chunk from an unauthorized, deleted or non-`ready` document is ever returned or passed to the LLM (security test SEC-03). | M2 / M5 |
| FR-RET-07 | Metadata filters (document subset). | A `document_ids` filter is intersected with the authorized set; it can never widen access. | M2 |
| FR-RET-08 | Optional cross-encoder reranking, behind a configuration flag. | Reranking is kept enabled by default only if the M4 evaluation justifies it. | M4 |

### 5.3 Generation (FR-GEN)

| ID | Requirement | Acceptance criterion | MS |
|---|---|---|---|
| FR-GEN-01 | An LLM provider interface with a Gemini adapter using `google-genai`. | The generation service depends only on the interface; tests use a fake provider. | M3 |
| FR-GEN-02 | The prompt is bounded by the evidence: system instructions are separate from evidence, and evidence is delimited and labelled as untrusted data. | The prompt snapshot test shows the expected structure; an injection fixture document does not change the system behaviour (SEC-07). | M3 |
| FR-GEN-03 | Structured output: `status`, `answer`, `citations[]` referencing evidence labels. | Output is parsed into a Pydantic model; invalid JSON leads to one bounded retry, then a safe error. | M3 |
| FR-GEN-04 | Abstain when evidence is insufficient (before the LLM is called, when the model reports it, or when validation finds no valid citations). | Unanswerable evaluation questions return `insufficient_evidence` and no answer text. | M3 |
| FR-GEN-05 | Handle contradictory evidence. | A fixture with conflicting pages returns `conflicting_evidence` and cites both sides. | M3 |
| FR-GEN-06 | Timeouts, bounded retries with backoff, safe provider errors. | A simulated timeout or 5xx gives HTTP 503 `llm_unavailable` with no provider message, key or stack trace in the body. | M3 |
| FR-GEN-07 | Every answered response carries a disclaimer. | `disclaimer` is a non-empty field in `QueryResponse`. | M3 |
| FR-GEN-08 | Citations are validated server-side against the evidence that was supplied. | Citations to unknown evidence labels are dropped; if none remain, the status becomes `insufficient_evidence`. | M3 |

### 5.4 Authentication, authorization and documents (FR-AUTH, FR-DOC)

| ID | Requirement | Acceptance criterion | MS |
|---|---|---|---|
| FR-AUTH-01 | Password login issuing a short-lived JWT (HS256; `iss`, `aud`, `exp`, `iat`, `sub`, `jti`). | Tampered, expired, wrong-issuer, wrong-audience and `alg=none` tokens are rejected with 401. | M5 |
| FR-AUTH-02 | Argon2id password hashing. | Stored hashes start with `$argon2id$`; verification works; rehash-on-login when parameters change. | M5 |
| FR-AUTH-03 | RBAC with `viewer`, `editor`, `admin`. | Every endpoint × role combination is covered by the authorization matrix test. | M5 |
| FR-AUTH-04 | Roles and active status are looked up per request (not trusted from the token). | Deactivating a user makes their existing token fail on the next request. | M5 |
| FR-DOC-01 | List and get only authorized documents; return 404 (not 403) for unauthorized document IDs. | IDOR test: user B gets 404 for user A's private document. | M5 |
| FR-DOC-02 | Delete a document: remove it from the indexes, delete its chunks, file and row, and record an audit event. | After deletion, queries never return its chunks; a FAISS rebuild does not resurrect it. | M5 |
| FR-DOC-03 | Store the original files privately under generated storage keys. | Storage paths never contain user-supplied filenames; files are not served statically. | M5 |

### 5.5 Query, feedback, UI, evaluation and operations

| ID | Requirement | Acceptance criterion | MS |
|---|---|---|---|
| FR-QRY-01 | `POST /chat/query` returns answer, status, citations (document, title, page, snippet), `query_id`. | The response validates against `QueryResponse`. | M5 |
| FR-FB-01 | Users can rate their own query (up/down + optional comment). | Feedback on another user's `query_id` returns 404; a duplicate returns 409. | M5 |
| FR-UI-01 | Streamlit login, upload, document list, chat with citations, feedback. | The UI calls only the public API with the user's token; manual E2E checklist passes. | M5 |
| FR-UI-02 | The UI renders model output as plain text (no HTML/Markdown execution). | An answer containing `![x](http://evil)` is displayed literally. | M5 |
| FR-EVAL-01 | Versioned evaluation dataset with page-level relevance labels. | The dataset has a version, a schema and a changelog; validation passes in CI. | M4 (seed in M2) |
| FR-EVAL-02 | Retrieval metrics Recall@k, MRR, nDCG@k. | Metric functions are unit-tested against hand-computed examples. | M2 |
| FR-EVAL-03 | Generation checks: citation validity/precision, abstention accuracy, key-fact coverage, optional LLM-judge faithfulness. | The report contains every metric and a snapshot of the configuration and model versions. | M4 |
| FR-EVAL-04 | Baseline and regression comparison. | The compare command exits non-zero when a metric regresses beyond its threshold. | M4 |
| FR-OPS-01 | Liveness and readiness endpoints. | Readiness returns 503 while the DB is unreachable or the index is stale or not loaded. | M5 |
| FR-OPS-02 | A CLI command rebuilds the indexes from canonical data. | A documented runbook procedure is tested in integration. | M2 / M6 |
| FR-OPS-03 | Audit events for security-relevant actions. | Login success/failure, upload, delete and authorization denial each write one audit row. | M5 |

## 6. Non-functional requirements

| ID | Category | Requirement | Verification |
|---|---|---|---|
| NFR-SEC-01 | Security | Unauthorized document text never reaches the LLM or the response. | SEC-03 spy-provider test |
| NFR-SEC-02 | Security | No secrets in source, images or logs; secrets come from the environment. | Secret scan in CI; log-redaction test |
| NFR-SEC-03 | Security | Error responses never include stack traces, SQL, provider messages or secrets. | SEC-09 |
| NFR-SEC-04 | Security | Rate limiting on login and query; request body size limits. | SEC-10 |
| NFR-PRIV-01 | Privacy | Raw questions, prompts and document text are not logged by default (`STORE_QUERY_TEXT=false`). | Log-capture test |
| NFR-PRIV-02 | Privacy | Deleting a document removes its file, chunks and vectors (hard delete); audit keeps only IDs and the checksum. | FR-DOC-02 test |
| NFR-PERF-01 | Performance (target) | Retrieval p95 ≤ 1.5 s on CPU at ≤ 50k chunks, excluding the LLM. | M4 latency report |
| NFR-PERF-02 | Performance (target) | End-to-end query p95 ≤ 10 s including Gemini. | M4 latency report |
| NFR-PERF-03 | Performance (target) | Ingesting a 50-page text PDF ≤ 60 s on CPU. | M1/M2 measurement |
| NFR-REL-01 | Reliability | Index files are written atomically; a crash during a write leaves the previous index usable. | Integration test |
| NFR-REL-02 | Reliability | Documents stuck in `processing` or `deleting` after a restart are reconciled at startup. | Integration test |
| NFR-OBS-01 | Observability | JSON structured logs with `request_id`; the `X-Request-ID` response header. | API test |
| NFR-MAINT-01 | Maintainability | Ruff clean; mypy on `src/`; ≥ 80% line coverage on `src/insureassist` (UI excluded). | CI |
| NFR-MAINT-02 | Maintainability | Evaluation runs are reproducible: dataset version, configuration, model names and git commit are recorded. | Evaluation report schema |
| NFR-PORT-01 | Portability | Runs on Windows (dev) and Linux containers. | Local and CI runs |

Performance numbers are **targets**. They will be measured in M4 and the measured results recorded; they are not guarantees.
